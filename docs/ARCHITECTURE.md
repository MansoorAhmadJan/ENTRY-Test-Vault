# Architecture — Entry-Test Knowledge Vault Dashboard (V4.0)

## Design goals, and how the architecture serves them

| Goal (from the V4.0 brief)                                        | How the architecture delivers it                                                                                                                                                                                                                                            |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fully offline, no server                                          | Data ships as `data/vault-data.js` (a `<script>` tag, not `fetch`), so the dashboard runs from a double-clicked `index.html` under `file://`. Hash-based routing (`js/core/router.js`) needs no server either.                                                              |
| Instant search at thousands of resources                          | `js/search/searchEngine.js` builds an inverted index (token → resource IDs) once at startup, not a re-scan per keystroke.                                                                                                                                                   |
| Scalable to thousands of resources                                | The data layer (`js/data/dataLoader.js`) builds `Map`-based indices (by ID, by university, by subject) instead of linear scans; filter/search operate on those, not on `VAULT_DATA` directly.                                                                               |
| Easy maintenance                                                  | Every module owns exactly one concern (see Module Map) and exposes a small public function set on `window.App.*`. Nothing outside `dataLoader.js` touches the raw `VAULT_DATA` shape.                                                                                       |
| Not hardcoded                                                     | All resource content lives in `data/vault-data.js`, generated by `/home/claude/vault/build-vault-data.js` from the Version 3.0 source data — never hand-authored, never inlined in HTML/JS.                                                                                 |
| Future compatibility (AI search, import wizard, cloud sync, etc.) | Every engine (`Search`, `Filter`, `Storage`) is called through a stable function interface. Swapping the inverted-index search for an AI-backed one, or `localStorage` for `IndexedDB`/cloud sync, means rewriting one module's internals — no call site elsewhere changes. |

## Module map

```
window.App = {
  Data:         js/data/dataLoader.js       // indices over VAULT_DATA; the ONLY module that reads the raw shape
  Search:       js/search/searchEngine.js   // inverted-index search + highlight()
  Filter:       js/search/filterEngine.js   // faceted AND/OR filtering over a resource list
  Storage:      js/storage/storageService.js // all localStorage reads/writes, namespaced "etv:*"
  Router:       js/core/router.js           // hash-based navigation, file:// safe
  State:        js/core/state.js            // minimal pub/sub store for cross-component UI state
  Theme:        js/core/themeManager.js     // light/dark + high-contrast, applies <html> attributes
  Config:       js/core/config.js           // nav structure, routes, keyboard shortcuts, app metadata
  ErrorHandler: js/core/errorHandler.js     // render guards + safe-call wrapper (V4.2)
  Diagnostics:  js/diagnostics/vaultDiagnostics.js // data-integrity checks (V4.2) + performance signals (V4.3)
  Perf:         js/core/perfMonitor.js     // startup timing marks, index/data size estimates (V4.3)
  FuzzyMatch:   js/utils/fuzzyMatch.js     // Levenshtein-based typo tolerance for search (V4.3)
  FocusTrap:    js/ui/focusTrap.js         // Tab-cycling + focus restoration for all modals (V4.3)
  ContextMenu:  js/ui/contextMenu.js       // right-click quick actions on resource cards (V4.3)
  VirtualList:  js/ui/virtualList.js       // windowed rendering for large List-view result sets (V4.3)
  Utils:        js/utils/helpers.js         // debounce, escapeHtml, groupBy, etc. (V4.2)
  Formatters:   js/utils/formatters.js      // star ratings, dates, badge colors (V4.2)
  Validators:   js/utils/validators.js      // resource shape validation (V4.2)
  Constants:    js/utils/constants.js       // enumerated value lists (V4.2)
  Icons:        js/ui/icons.js              // inline SVG icon library
  Dom:          js/ui/dom.js                // el()/qs()/delegate() helpers (V4.2)
  Toast:        js/ui/toast.js              // notification component (V4.2)
  Components:   js/ui/{resourceCard,resourceModal,sidebar,header,breadcrumbs,filterPanel,shortcutsModal,commandPalette}.js
  Views:        js/views/{home,browse,collection,queue,stats,diagnostics,settings}View.js
  init:         js/app.js                   // bootstrap sequence, wires the above together
}
```

### V4.2 additions at a glance

- **Reusable components** (`js/ui/`): `resourceCard.js` and `resourceModal.js` are each called from multiple views (Home, Browse, Favorites, Bookmarks, Progress) — one implementation, several call sites, per the "no duplicated logic" requirement.
- **Views** (`js/views/`): one file per route, each exporting a single `(container, route) => void` function registered on `App.Views`. `app.js` looks up the handler by `route.view` — adding a new page later means adding one file and one registry entry, not touching the router or shell.
- **Error handling**: `App.ErrorHandler.guard(container, label, fn)` wraps every view render; a thrown error inside one view shows an inline error card in that view's container instead of crashing the whole app. `App.ErrorHandler.safeCall` wraps individual storage writes the same way.
- **Diagnostics page** (`#/diagnostics`): runs `App.Diagnostics.run()` (structural checks — duplicate IDs, malformed URLs, invalid enum values, dangling `relatedResources` references) plus a "System Health" tab that carries over the V4.1 module self-test, so that capability persists now that `index.html` shows the real UI instead of a diagnostic-only landing page.

## Script load order (see `index.html`)

1. **`data/vault-data.js`** — must exist before anything reads `window.VAULT_DATA`.
2. **Core infrastructure with no cross-dependencies** — `icons.js`, `state.js`, `router.js`, `storageService.js`. Order among these four doesn't matter.
3. **Data-dependent engines** — `dataLoader.js` (reads `VAULT_DATA`), then `searchEngine.js` and `filterEngine.js` (both call `App.Data.*`, so `dataLoader.js` must load first among this group, though it does not need to have _run_ `init()` yet — they only call `App.Data.getAll()` etc. when their own `build()`/`apply()` runs, by which point `app.js` has already called `App.Data.init()`).
4. **`js/app.js`** — bootstrap, must load last. Calls `App.Data.init()` → `App.Search.build()` → wires `Filter`/`Storage`/`Router`/`State`, in that order, on `DOMContentLoaded`.

This order is enforced by plain `<script>` tags (no bundler, per the "no frameworks unless absolutely necessary" instruction) — see the comments in `index.html` itself.

## Why no framework

The brief allows one "unless absolutely necessary." At ~100–2,000 resources, an inverted-index search plus `Map`-based lookups is fast enough that a virtual-DOM framework buys nothing except a build step, which directly fights the "fully offline / open the file / no install" requirement. If the vault grows into the tens of thousands of resources and the render layer (V4.2) starts to show jank on large filtered lists, revisit this decision — the module boundaries above are what make that an isolated change (rewrite the UI layer's rendering, not `Data`/`Search`/`Filter`/`Storage`).

## Data flow for a typical interaction (once V4.2 UI exists)

```
User types in search box
  → UI layer reads input, debounces
  → App.Search.search(query) → ranked Resource[]
  → App.Filter.apply(results, currentFilterState) → filtered Resource[]
  → UI layer renders cards, calling App.Search.highlight(field, query) per field
  → User clicks a resource card
  → App.Storage.pushRecentlyViewed(id)
  → App.Router.navigate('resource/' + id)
  → UI layer reads App.Data.getById(id) + App.Storage.getProgress(id)/isFavorite(id) to render the modal
```

## Data regeneration

`data/vault-data.js` (and its `data/vault-data.json` twin) are generated, not hand-written. Source: `/home/claude/vault/build-vault-data.js`, which reads the Version 3.0 vault's `data_v3.js` and maps each field 1:1 (see `data/schema.md` for the exact mapping and the reasoning behind the `.js`-not-`.json` choice). Re-run it any time the underlying vault data changes:

```bash
cd /home/claude/vault
node build-vault-data.js
```

This never touches `localStorage` — a fresh data export cannot erase anyone's tracked progress, favorites, or bookmarks, because those live entirely in the browser (see `js/storage/storageService.js`).

## What V4.3 actually tested (not just wrote)

- **A real bug was found and fixed, not just claimed fixed**: `resourceModal.open()` synchronously moved focus to its close `<button>` while a physical Enter keypress was still being processed (e.g. from the header search box or command palette). The browser then fired a native click on that now-focused button on keyup, instantly closing the modal that had just opened — a genuine race condition, not a logic error visible from reading the code. Caught via real `page.keyboard.press('Enter')` in Chromium (a synthetic `dispatchEvent` call did _not_ reproduce it — only actual OS-level key simulation did), fixed by deferring the focus move one tick, and re-verified from both the header search and the command palette afterward.
- **Fuzzy search was verified to actually tolerate typos**, not just implemented: querying `"mathmatics"` (missing an 'e') returns mathematics-related resources via the Levenshtein fallback, confirmed by inspecting actual result titles, not just checking the function didn't throw.
- **Virtual scrolling was stress-tested at 5,000 synthetic items**, not just the real 102-resource vault (which never exceeds the virtualization threshold): confirmed only ~16–22 DOM rows exist at any scroll position, confirmed scrolling to `scrollTop: 100000` on 40px rows correctly renders row ~2494, and confirmed the real vault's List view (102 resources, below the 150-resource threshold) correctly uses plain rendering instead — so the "don't over-engineer small data" claim in the code's own comments is backed by an actual assertion, not just written down.
- **Focus trap was verified with 15 consecutive Tab presses** inside an open resource modal (never escaped) and confirmed to restore focus to the exact card element that opened it after closing — an actual DOM assertion, not a visual impression.
- **PWA service worker was tested in both failure and success modes**: confirmed zero console errors and no registration under `file://`, then separately confirmed an actual `ServiceWorkerRegistration` exists when the same files are served via a local `http://` server — both branches of the defensive registration code were exercised, not just the happy path.
- **The Diagnostics Performance tab's own numbers were caught being wrong and fixed during this build**: "Total Startup Time" initially computed live elapsed-time-since-boot (a number that grows the longer the tab stays open) instead of a fixed boot duration — caught by waiting 3 seconds before checking the displayed value and seeing it change, then fixed to use a frozen delta between two recorded marks, then re-verified the value no longer drifts.

## What V4.2 actually tested (not just wrote)

Every claim below was verified by driving a real headless Chromium instance (Playwright), not inferred from reading the code:

- Full click-through: Home → Browse → search "mathematics" → open a resource → toggle favorite → close modal → Favorites page shows it → toggle theme → global header search → Diagnostics → Statistics → Settings. Zero console errors across the whole sequence.
- Pagination: "Load more" correctly grows the visible set (60 → 102, the vault's actual resource count).
- Keyboard shortcuts: Ctrl+K focuses the header search input; `?` opens the shortcuts modal; both confirmed via actual `page.keyboard.press()`, not just code review.
- Responsive drawer: at ≤900px width the sidebar's bounding box is confirmed off-screen (`x: -240`) by default and on-screen (`x: 0`) after toggling — an actual layout assertion, not just a CSS rule that looks right.
- Persistence: theme, high-contrast, and sidebar-collapsed state were all confirmed to survive a full `page.reload()`.
- Diagnostics accuracy: running `App.Diagnostics.run()` against the real 102-resource vault reports zero issues — confirming the V3.0 data audit's cross-reference model reads back cleanly through the new structural validator, not just that the validator runs without crashing.
- Accessibility spot-check: an automated sweep found 2 icon-only buttons missing `aria-label` (Browse's grid/list view toggles) — both were fixed before this was shown to you, not left as a known issue.
